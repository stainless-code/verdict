`verdict run --agent claude` now writes its review without a manual permission flag. Every claude launch carries one grant scoped to that launch's own bundle directory (`--allowedTools=Edit(./.verdict/state/<bundle>/**)`), so the agent writes `review.json` and nothing else: a review still cannot edit source. The grant is built from the resolved directory and never widens past it: a symlinked `.verdict`, `.verdict/state` or bundle directory is refused (`bad-config`), and a path the rule syntax cannot carry launches without the grant and with a warning. A symlink at a path the launch writes or reads back (`review.json`, `verdicts.json`, `launcher.json`, `.run.out`) refuses the new `artifact-path-unsafe` before any agent starts, so a checked-in `review.json -> ../src/main.go` cannot aim the write at source. Your own permission flag after `--` (`--permission-mode`, `--dangerously-skip-permissions`, `--allowedTools`, `--add-dir`, `--tools`) drops the grant. The shell restriction now stays beside an additive or tightening tool flag: claude's `--allowedTools`/`--disallowedTools` sit beside it, and pi's `--exclude-tools` and bob's `--disable-tool-groups` get verdict's value merged in (`--exclude-tools bash,powershell,markdown`); only a flag that replaces the whole tool set, or `--allow-shell`, drops it. The `no-review-artifact` hint no longer suggests the broader `--permission-mode acceptEdits` for claude, and `init --ci` workflows name the grant in their comment.

`verdict loop` now works with stock agent setups. Its fix spawn carries the agent's documented edit grant (claude `--permission-mode acceptEdits` with Bash and PowerShell still denied, codex `--sandbox workspace-write`, none for other agents). `verdict loop … -- <agent args>` passes arguments to every spawn after that grant; since they also reach the review of untrusted content, they are an allowlist: only the agent's model flag with one value (`-- --model opus`), anything else refuses `bad-flags`. `--print` shows each grant in the exact argv. **Breaking (pre-1.0):** loop's verify step, which runs the fix agent's own command, is now sandboxed by default (as `verify --sandbox`); a host without the sandbox refuses `sandbox-unavailable`. Pass `--sandbox-network-only` or the new `--no-sandbox` (which warns) to opt out; `--sandbox` still works and is now a confirmation. New `verdict loop --max-severity critical|important|informational` (default `important`) has `gate`'s meaning, so an informational finding no longer holds the loop; `--max-severity informational` restores the strict gate.

The review handoff (`procedure.md` and each finder's procedure) now asks the agent for the `coverage[]` attestation the default `gate` requires (`[]` when nothing changed; `chunks[]` on a chunked bundle), and the two-finder union keeps an empty attestation. Before, every `run --agent` review — including the workflows `init --ci` generates — failed the default gate on coverage, and `verdict loop` on a clean tree could never pass. Loop's stop line also names a refusal's code once instead of twice.

`verdict run --require-coverage` carries `record --require-coverage` into the launch: a review missing its coverage attestation gets a repair round naming the new `coverage-incomplete` problem, and a run that ends with only that gap refuses `coverage-incomplete` as record would. On a chunked bundle a `chunks[]` that names no chunk (absent, `false`, or empty) is the gap, for `record --require-coverage` and `post --require-coverage` too. With two finders the union's attestation is what counts: it is checked before any cross-check runs, and `--resume` seals the flag. The loop's review step passes it, so a review that omits `coverage[]` is repaired instead of stopping the loop at record.
