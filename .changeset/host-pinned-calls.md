Every `gh` and `glab` call for a target resolved from a URL or the `origin` remote (and for `demo <url>`) now names that target's host itself, so `GH_HOST`, `GITLAB_HOST`, or the CLI's default host can no longer send a fetch, a thread reply, or a review to another host's pull request with the same `owner/repo` and number. The calls name it: `gh api --hostname <host>`, `gh pr … --repo <host>/<owner>/<repo>`, `glab api --hostname <host>`, `glab mr … -R https://<host>/<path>`. `post` always posts to the host its bundle was fetched from. The new typed refusal `host-mismatch` (exit 1) names both hosts when no call can be pinned: a Forgejo target on another host than `FORGEJO_HOST`; a GitHub or GitLab host on a non-default port (neither CLI's `--hostname` takes one); an SSH GitLab origin whose host `GITLAB_HOST` serves on another port; a bundle fetched from another host than the target; a real post of a GitHub or GitLab bundle with no recorded URL under a typed pair; or a `gh`/`glab` argv whose host or repository the pin cannot control. Host equality now compares the authority, so two hosts that differ only by a non-default port are different hosts. Migration: if `post` refuses with `host-mismatch`, re-fetch the target or pass a target on the bundle's host. A typed `<owner/repo> <pr>` (CLI, MCP, or SDK) names no host, so its reads still follow the host CLI's own default; `post` always pins to its bundle's host. See `docs/manual.md` § Targets.
