**Behavior change:** a `VERIFIED` claim in `verification.json` no longer flips a finding to `addressed` on its own. `record` and `post` now also require the bundle's `verify-receipt.json`. Only `verdict verify` writes that file, and it records the command verify ran, the finding sig `patch.json` names, the exit, the timeout, and the checked-out head. A claim flips only when that receipt shows exit 0, no timeout, the claim's exact `verifyCmd`, the claim's finding when the receipt names one, and a head equal to the HEAD being graded. Before, a hand-written claim with a matching `resultHead` was enough, and a failing or timed-out run only drew a warning. A pass written into `patch.json` is not a receipt.

Without a matching receipt the finding keeps its status, the claim is logged as a `revalidation` history event, and the run warns `VERIFIED claim for <sig> not applied (<reason>)`. `gate`, `report --check`, `post --approve`, MCP and `serve` all read the status this merge settles, so none of them can pass a finding on a claim nobody observed. `NOT VERIFIED` still reopens without a receipt. A `triage[]` claim for `addressed` is now ignored with a warning, as the docs already said: no rationale buys it.

`verdict verify` now runs the command in the repo root. It records a head only when the working tree is clean and the same commit is checked out before and after the command. Otherwise it warns and records no head, so commit the fix before you verify it. The status check ignores only verdict's bundle state (`.verdict/state/`), `verdict loop`'s round receipts (`.verdict/loop/`), and the generated `.verdict/.gitignore`. It refuses a symlinked bundle directory and writes only through the bundle directory it pinned before the command ran. A bundle moved or replaced mid-run records nothing, and the previous receipt is deleted before the command starts. The status check always counts untracked files and submodules, whatever the checkout's status config says. `verify --group` follows the same clean-tree rule: a dirty tree refuses as `head-mismatch`, and a tree the command leaves dirty fails its receipt. A receipt's finding sig must resolve to exactly one finding in the store, and both receipt readers reject trailing data after the JSON object. The `fix` instructions now follow fix → commit (and push plus re-fetch for a PR, or re-run `fetch-local` for a local bundle) → `verdict verify` → land. The receipt defends against claims nobody observed, not against a process with the operator's own file access. `docs/manual.md` and `SECURITY.md` state that threat model.
