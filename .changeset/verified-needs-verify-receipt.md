**Behavior change:** a `VERIFIED` claim in `verification.json` no longer flips a finding to `addressed` on its own. `record` and `post` now also require the bundle's `verify-receipt.json`. Only `verdict verify` writes that file, and it records the command verify ran, the finding sig `patch.json` names, the exit, the timeout, and the tree of the content it ran on. A claim flips only when that receipt shows exit 0, no timeout, the claim's exact `verifyCmd`, the claim's finding when the receipt names one, and a tree equal to the graded content's (see the content-bound receipts entry). Before, a hand-written claim with a matching `resultHead` was enough, and a failing or timed-out run only drew a warning. A pass written into `patch.json` is not a receipt.

Without a matching receipt the finding keeps its status, the claim is logged as a `revalidation` history event, and the run warns `VERIFIED claim for <sig> not applied (<reason>)`. `gate`, `report --check`, `post --approve`, MCP and `serve` all read the status this merge settles, so none of them can pass a finding on a claim nobody observed. `NOT VERIFIED` still reopens without a receipt. A `triage[]` claim for `addressed` now refuses the review, as the docs already said: no rationale buys it.

`verdict verify` refuses a symlinked bundle directory and writes only through the bundle directory it pinned before the command ran. A bundle moved or replaced mid-run records nothing, and the previous receipt is deleted before the command starts. A receipt's finding sig must resolve to exactly one finding in the store, and both receipt readers reject trailing data after the JSON object. The receipt defends against claims nobody observed, not against a process with the operator's own file access. `docs/manual.md` and `SECURITY.md` state that threat model.
