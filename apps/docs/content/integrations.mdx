Verdict is one binary. Every surface below calls the same review core and
returns the same data as `--json`. Pick the one that matches who calls it.

| You are…                              | Use                                     |
| ------------------------------------- | --------------------------------------- |
| An agent harness with a skills folder | [Skill and CLI](#skill-and-cli)         |
| An agent host that speaks MCP         | [MCP server](#mcp-server)               |
| A Go program                          | [Go SDK](#go-sdk)                       |
| A Node or Bun program                 | [TypeScript client](#typescript-client) |
| Any other language                    | [JSON schemas](#json-schemas)           |

The MCP server, the Go SDK, and the TypeScript client are experimental until
1.0. The `--json` envelope and the schemas are versioned separately with
`schema_version: "1"`, and that contract is the stable part.

## Skill and CLI

The binary carries its own skill: `SKILL.md`, the prompts, and the schemas.
Install it into your agents with one command:

```bash
verdict skill install --detect
```

`--detect` installs into every agent whose skills directory already exists and
is non-empty. To target one agent, pass `--agent` with `claude`, `cursor`,
`codex`, `opencode`, `copilot`, `gemini`, `goose`, `qwen`, `windsurf`, or
`agents`. To install into any other directory, pass `--dir <skills-dir>`.

```bash
verdict skill install --agent claude --dry-run   # preview: create, update, keep, blocked
verdict skill install --agent claude             # write it
```

The install is atomic, writes a `.verdict-managed` receipt, and refuses to
touch a directory it did not create unless you pass `--force`. It never
prompts and makes no network call.

Prefer the registry? `npx skills add stainless-code/verdict` installs the same
skill. Install one way per machine, or the agent loads the skill twice.

## MCP server

`verdict mcp` serves the review verbs as MCP tools over stdio. It has no
daemon, no HTTP mode, and no auth of its own: it runs with your credentials
and exits when stdin closes. Print or write the host config in one command:

```bash
verdict mcp config --agent claude --write
```

That merges this entry into the project's `.mcp.json`:

```json
{ "mcpServers": { "verdict": { "command": "verdict", "args": ["mcp"] } } }
```

`--agent` takes `claude`, `cursor`, or `codex`. Without `--write` the command
only prints the entry. It backs up the old file to `<path>.verdict.bak` and
refuses a file it cannot parse.

Two flags change what the server exposes:

- `--read-only` exposes only tools that neither submit a review nor rewrite
  the bundle: `report`, `next`, `show`, `trend`, `ready`, `doctor`, and
  `check-tree`.
- `--operator` adds `triage`. Status changes are the human's call, so an agent
  proposes them in `review.json` and never gets the tool by default.

Each tool returns the CLI envelope's `data`. A typed refusal comes back with
`isError: true` and `{code, message, hint}`. The
[manual](/manual#mcp-server-stdio-experimental-until-10)
has the full tool list.

## Go SDK

`pkg/verdict` runs the verbs in-process. It takes typed requests, never calls
`os.Exit`, and never touches your stdio.

```bash
go get github.com/stainless-code/verdict/pkg/verdict
```

```go
package main

import (
	"context"
	"errors"
	"fmt"

	"github.com/stainless-code/verdict/pkg/verdict"
)

func main() {
	c := verdict.New(verdict.Options{})
	defer c.Close()

	resp, err := c.Report(context.Background(), &verdict.ReportRequest{
		Invocation: verdict.Invocation{Repo: "acme/app", PR: "123"},
	})
	var refusal *verdict.RefusalError
	if errors.As(err, &refusal) {
		fmt.Println(refusal.Code, refusal.Hint)
		return
	}
	if err != nil {
		panic(err)
	}
	fmt.Println(resp.Human[0])
	fmt.Println(resp.Next)
}
```

Run it from the checkout that holds `.verdict/state/`, like the CLI. With a clean
bundle for `acme/app` PR 123 it prints:

```text
report: .verdict/state/123 (0 shown) open=0 head=aaaaaaa
none open — nothing to address
```

Install, upgrade, and skill verbs stay CLI-only and are not in the SDK.

## TypeScript client

One npm install brings the binary and the client:

```bash
npm i @stainless-code/verdict
```

```ts
import {
  createClient,
  VerdictRefusalError,
} from "@stainless-code/verdict/client";

const verdict = createClient({ cwd: "path/to/repo" });

const report = await verdict.report(["acme/app", "123"]);
console.log(report.data.verdict.open, "open findings");

try {
  await verdict.report(["acme/app", "9999"]);
} catch (error) {
  if (error instanceof VerdictRefusalError) {
    console.log(error.code); // "missing-findings"
    console.log(error.hint); // "try: run the fetch/record step named above first, then re-run"
  }
}
```

The client spawns `verdict <verb> … --json`, reads one envelope, and maps the
exit codes to typed errors. It finds the binary through `VERDICT_BIN`, then
the platform package, then `PATH`. It has no dependencies and starts no server.
Every review verb has a named method and its own typed `data`; keep
`verdict.run(verb, args)` for a verb or field the client has not typed yet.

## JSON schemas

The envelope and every store file are published as JSON Schema (draft 2020-12)
under
[`skills/verdict/schemas/`](https://github.com/stainless-code/verdict/tree/main/skills/verdict/schemas). They
ship in the npm package and inside the binary. List them from a clean install:

```bash
verdict skill files | grep schemas/
```

Check an agent-written review before you post it:

```bash
schemas/validate.sh schemas/review.schema.json .verdict/state/123/review.json
```

The script exits `0` when the file is valid and prints one `FAIL` line per
problem otherwise. It is the same checker the tests use. Run it from your
installed skill's directory, or from `skills/verdict/` in a checkout.

To generate a client for another language, point a code generator at
`skills/verdict/schemas/envelope.schema.json`. [Build a client](/build-a-client) walks through
Python end to end.
