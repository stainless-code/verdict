Three steps: install the binary, add the skill, review a PR. Right after step 1,
`verdict demo` runs the whole loop with no other setup. The
[introduction](/docs/introduction) states the loop those steps implement.

<Callout type="info" title="Requirements">
  `git`, plus the CLI for your host. For GitHub that is `gh`, signed in (`gh
  auth login`) with `repo` scope. Run `verdict doctor` after installing to check
  your setup.
</Callout>

## Try it first, with no setup

`verdict demo` reviews one change with no configuration: it writes nothing in
your repository and cannot post. It reads with `gh` when you are signed in, over the
anonymous GitHub API otherwise, and launches the first agent CLI on `PATH`.

```bash
verdict demo https://github.com/owner/repo/pull/123   # any public GitHub PR
verdict demo                                          # your own working tree
```

<Steps>
  <Step title="Install">
    Pick your package manager or OS. Every route installs the same release
    binary.

    <InstallSwitcher />

    The install scripts take `VERDICT_VERSION=vX.Y.Z` to pin a version — on the
    script half of the pipe:
    `curl -fsSL https://stainless-code.com/verdict/install.sh | VERDICT_VERSION=vX.Y.Z sh`
    (Windows: `-Version vX.Y.Z`). Both verify the archive's SHA-256 and, with
    `cosign`, the release signature, and install to
    `~/.verdict/bin` with no root rights. Update later with `verdict upgrade`;
    it runs only when you type it. In CI, the
    [`setup-verdict` action](https://github.com/stainless-code/verdict#ci)
    installs a pinned, verified binary.

    `npx` and `bunx` run it once without installing; pnpm's release-age gate can
    serve the previous release for a day, so pin the exact version or add
    `--config.minimumReleaseAge=0`.

  </Step>
  <Step title="Add the skill">
    ```bash
    verdict skill install --detect
    ```
    This installs the skill into every agent whose skills directory already
    exists and is non-empty. To target one agent, pass `--agent` with `claude`,
    `cursor`, `codex`, `opencode`, `copilot`, `gemini`, `goose`, `qwen`,
    `windsurf`, or `agents`.
    The skill ships inside the binary, so it always matches your version.

    You can also install it from the registry with
    `npx skills add stainless-code/verdict`. Use one route per machine.

  </Step>
  <Step title="Review a PR">
    Fetch the PR into a bundle:

    ```bash
    verdict fetch owner/repo 123
    ```

    This writes `.verdict/state/123/` with the diff, metadata, threads, and file roles.
    On GitHub it needs no clone.

    Then launch your agent on the bundle:

    ```bash
    verdict run owner/repo 123 --agent claude --budget auto
    ```

    `--agent` takes any of the 46 names in `verdict run --help`; `--budget auto`
    sizes the depth from the diff (`light` one finder, `standard` and `deep` two).

    The skill tells the agent how to work: read the whole diff first, ask
    read-only lens subagents one falsifiable question each when the answer could
    change the verdict, and write exactly one `.verdict/state/123/review.json`.

    Post the review:

    ```bash
    verdict post owner/repo 123
    ```

    This checks every anchor against the diff hunks, turns suggestions into
    GitHub suggestion blocks, and submits one review. `--dry-run` validates and
    previews the payload without posting.

  </Step>
  <Step title="Read the report">
    ```bash
    verdict report owner/repo 123
    ```
    One offline read of the store: ranked open findings, the verdict, and
    counts. `verdict next` names the top finding and the command to act on it.
    `report --json` returns the same data for a script.
  </Step>
  <Step title="Re-review new commits">
    ```bash
    verdict fetch owner/repo 123 --base-sha <prior-reviewed-sha>
    ```
    Then have your agent review with `prompts/incremental-review.md` instead of
    `prompts/review.md`. Recorded findings are not reported again, and threads
    retire by rule. Incremental fetch runs on GitHub and GitLab.
  </Step>
  <Step title="Review local changes">
    No PR yet? Bundle the working tree instead:

    ```bash
    verdict fetch-local owner/repo work
    ```

    Ask your agent to review `.verdict/state/local-work/`, then merge its findings:

    ```bash
    verdict record owner/repo local-work
    ```

    Nothing is posted. Pick the diff with `--staged`, `--range A..B`,
    `--base <ref>`, or `--stash`. When a PR exists later,
    run `verdict fetch owner/repo 123`, then
    `verdict adopt owner/repo 123 --from local-work` to carry the findings over.

  </Step>
</Steps>

## Optional: scaffold repo defaults

```bash
verdict init --preset standard     # chill|standard|strict
verdict init --ci github           # or --ci forgejo, --ci gitlab; --print previews
```

This writes starter control files under `.verdict/` — a budget, a panel, and
knowledge-base rules — and validates them. Reviews work without it. `--ci` adds
the every-PR workflow; [Gate a PR in CI](/docs/ci-gate) covers each host.

## Other hosts

`fetch --provider` also reads `gitlab`, `gitcafe`, `forgejo`, `bitbucket`, and
`azure`; `post` submits to GitHub, GitLab, and Forgejo. GitLab has no
request-changes event, so that verdict posts as a comment. `record`, `report`,
`triage`, `show`, and `next` run on any bundle, `ready` and live `calibrate` on
GitHub and GitLab, `calibrate --probe` anywhere. Auth and gaps per host are in
the [manual](https://github.com/stainless-code/verdict/blob/main/docs/manual.md#providers-non-github-hosts).
