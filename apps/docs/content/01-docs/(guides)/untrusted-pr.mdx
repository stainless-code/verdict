Use this when the diff is untrusted: an unknown author, a drive-by fork PR, or a patch arriving as text. Fetching and reading are safe; executing the claimed fix is not — so the verify step, never the whole review, runs inside a throwaway sandbox.

<Steps>
  <Step title="Check the head out and fetch the PR as data">
    ```bash
    git fetch origin pull/123/head
    git -c core.hooksPath=/dev/null worktree add --detach ../pr-123 FETCH_HEAD
    cd ../pr-123 && verdict fetch owner/repo 123
    ```

    A `VERIFIED` claim binds only when the verify receipt names the PR head's tree, so work in a throwaway worktree of that head, never your own. Checking it out runs none of its code (hooks are off), and `fetch` only writes the bundle into that checkout's `.verdict/state/`. The agent review reads the bundle and records claimed fixes with a `verifyCmd`, the one thing you do not yet trust: do not run it yourself.

  </Step>

  <Step title="Run the verify step sandboxed">
    ```bash
    verdict verify owner/repo 123 --sandbox
    ```

    `verify` copies the worktree's content into a private snapshot and runs the command there. On Linux with `bubblewrap` installed, the command gets its own PID namespace and loopback, no route out, an empty `/run`, a private `/tmp`, and every host credential path (`~/.aws`, `~/.ssh`, `~/.config/gh`, and the rest) replaced. On macOS a `sandbox-exec` profile denies the network (loopback included), every Mach service (so the keychain, the clipboard, `defaults`, `open`, and `osascript` cannot act for it), writes outside the snapshot and a private `TMPDIR`, and reads of the credential paths and shared temp roots. It is a policy, not a mount namespace: the rest of the filesystem stays readable, so full isolation on a Mac needs a Linux VM or container running the bubblewrap recipe. The patch record and the `--json` envelope carry `"sandboxed": true` and `sandboxMechanism`. The repository's git control files are read-only, so nothing the command does runs later when you use git: `git status` works, `git commit` does not.

    Linux hosts without `bubblewrap` can opt into `--sandbox-network-only` instead. It removes the network and nothing else — the host filesystem, other processes' environments, and filesystem unix sockets such as `docker.sock` stay reachable — so it records `sandboxMechanism: "unshare-net"` and never `"sandboxed": true`.

  </Step>

  <Step title="Read the refusals">
    Two layers can stop the run, and both refuse before anything executes. The static gate rejects hostile shapes up front — [`verify-networked`](/docs/troubleshooting#verify-networked) for pipe-to-shell fetches, plus `verify-destructive`, `verify-credential-read`, and `verify-repo-escape` — each quoting the matched fragment with a `try:` rewrite hint. The sandbox is the second layer for what the static gate cannot see: when the host has no mechanism (Linux needs `bwrap`, macOS needs a working `sandbox-exec`), `bwrap` is missing, or user namespaces are restricted, `verify` refuses [`sandbox-unavailable`](/docs/troubleshooting#sandbox-unavailable) with exit `1`, names the cause, and runs nothing. It never silently falls back to an unsandboxed command.
  </Step>
</Steps>

## What success looks like

On Linux and macOS the claimed command runs contained and the patch record notes `"sandboxed": true` with its `sandboxMechanism`. Anywhere else you get `sandbox-unavailable`, the patch file stays byte-identical, no `.verify.out` is written, and exit `1` tells the caller the proof did not run. Either way, nothing untrusted reached your network; your credential paths are hidden on both platforms, the keychain is unreachable on macOS, and full mount isolation on macOS needs a Linux VM or container running the bubblewrap recipe. Once the proof runs, the normal merge protection still applies: [Gate a PR in CI](/docs/ci-gate). Remove the worktree with `git worktree remove ../pr-123`.
