Use this when the diff is untrusted: an unknown author, a drive-by fork PR, or a patch arriving as text. Fetching and reading are safe; executing the claimed fix is not — so the verify step, never the whole review, runs inside a throwaway sandbox.

<Steps>
  <Step title="Fetch the PR as data">
    ```bash
    verdict fetch owner/repo 123
    ```

    `fetch` only writes the bundle (`PR.json`, `full.diff`, `toc.txt`): no checkout, no execution. The agent review reads that bundle and records claimed fixes with a `verifyCmd`, which is the one thing you do not yet trust. Keep it that way: do not check out the fork, do not apply the patch to your worktree, and do not run the claim yourself first.

  </Step>

  <Step title="Run the verify step sandboxed">
    ```bash
    verdict verify owner/repo 123 --sandbox
    ```

    On Linux with `bubblewrap` installed, `verify` builds the sandbox itself: the command gets its own PID namespace and loopback, no route out, an empty `/run`, a private `/tmp`, and every credential path on the host (`~/.aws`, `~/.ssh`, `~/.config/gh`, and the rest) replaced before the command runs. On macOS it builds a `sandbox-exec` profile instead: it denies the network — every `bind()` and `connect()`, loopback included — and every Mach service (so the keychain, the clipboard, `defaults`, `open`, and `osascript` cannot act for it), denies every write outside the reviewed root and a private per-run `TMPDIR` (so no LaunchAgent or shell rc file can be planted), and denies reads of the credential paths and the shared host temp roots. It is a policy, not a mount namespace: the rest of the host filesystem stays readable, so full isolation on a Mac needs a Linux VM or container running the bubblewrap recipe. The patch record carries `"sandboxed": true` and `sandboxMechanism`, and the `--json` envelope reports both the same way. On either platform the command can write the working tree, which is the PR's own content anyway, but not the repository's git control files: hooks, `.git/config`, and the rest of the git directory are write-denied, so nothing it does there runs later when you use git. `git status` and `git diff` still work; `git commit` inside the sandbox does not.

    Linux hosts without `bubblewrap` can opt into `--sandbox-network-only` instead. It removes the network and nothing else — the host filesystem, other processes' environments, and filesystem unix sockets such as `docker.sock` stay reachable — so it records `sandboxMechanism: "unshare-net"` and never `"sandboxed": true`.

  </Step>

  <Step title="Read the refusals">
    Two layers can stop the run, and both refuse before anything executes. The static gate rejects hostile shapes up front — [`verify-networked`](/docs/troubleshooting#verify-networked) for pipe-to-shell fetches, plus `verify-destructive`, `verify-credential-read`, and `verify-repo-escape` — each quoting the matched fragment with a `try:` rewrite hint. The sandbox is the second layer for what the static gate cannot see: when the host has no mechanism (Linux needs `bwrap`, macOS needs a working `sandbox-exec`), `bwrap` is missing, or user namespaces are restricted, `verify` refuses [`sandbox-unavailable`](/docs/troubleshooting#sandbox-unavailable) with exit `1`, names the cause, and runs nothing. It never silently falls back to an unsandboxed command.
  </Step>
</Steps>

## What success looks like

On Linux and macOS the claimed command runs contained and the patch record notes `"sandboxed": true` with its `sandboxMechanism`. Anywhere else you get `sandbox-unavailable`, the patch file stays byte-identical, no `.verify.out` is written, and exit `1` tells the caller the proof did not run. Either way, nothing untrusted reached your network; your credential paths are hidden on both platforms, the keychain is unreachable on macOS, and full mount isolation on macOS needs a Linux VM or container running the bubblewrap recipe. Once the proof runs, the normal merge protection still applies: [Gate a PR in CI](/docs/ci-gate).
