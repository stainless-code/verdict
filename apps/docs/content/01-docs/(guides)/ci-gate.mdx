Use this when CI should block the merge on review findings: one workflow file, one composed exit code, no new secrets leaving your runners.

<Steps>
  <Step title="Write the workflow">
    One offline command writes it for your host:

    ```bash
    verdict init --ci github          # .github/workflows/verdict-review.yml
    verdict init --ci forgejo         # .forgejo/workflows/verdict-review.yml
    verdict init --ci gitlab          # .gitlab/ci/verdict-review.yml
    ```

    `--agent` picks one of the 46 built-in launchable agents (`init --ci` resolves
    against the catalog, not your `settings.json`) and `--key-secret` names the
    repository secret. Or copy the recipe from `docs/ci-recipe.md`:

    ```bash
    cp examples/verdict-review.yml .github/workflows/verdict-review.yml
    ```

    Either way the GitHub pipeline is `ready --check`, `fetch`, `run --agent` (your
    agent, your key, writes `review.json`), `post`, then the merge gate. Require
    the job in branch protection; per-host runner prerequisites are in the
    manual's [Every PR](https://github.com/stainless-code/verdict/blob/main/docs/manual.md#every-pr).
    Rehearse the loop on a branch first:
    [Review a branch without a PR](/docs/local-review).

  </Step>

  <Step title="Keep the gate step as the single decider">
    The workflow ends with the composed check:

    ```bash
    verdict gate "$GITHUB_REPOSITORY" "${{ github.event.pull_request.number }}" \
      --max-severity critical --require-head --live auto
    ```

    At least one dimension is required: `--max-severity critical|important|informational` (open findings at or above the tier) and/or `--require-head` (a completed post for the fetched HEAD); `--coverage` alone is a usage error. Coverage defaults to `require`, so a partial `coverage[]` attestation fails instead of merging — pass `--coverage warn` to migrate. `--live auto` keeps an unreachable lookup neutral; `--live strict` fails closed. Only `open` findings count.

  </Step>

  <Step title="Read the exit code">
    | Code | Meaning                                                        |
    | ---- | -------------------------------------------------------------- |
    | `0`  | pass: every requested dimension is clean (`gate: PASS`)        |
    | `1`  | fail or unknown: the `gate:` lines name the failing dimensions and one `try:` hint gives the recovery |
    | `2`  | usage error: a dimension is missing or a flag is wrong — check the invocation |
    | `3`  | tool error: the bundle, auth, or store is broken — inspect, then retry |

    There is no `--force`: triage or fix, then re-fetch and re-run. The advisory `verdict report` step stays the escape hatch.

  </Step>
</Steps>

## What success looks like

The job log closes with `gate: PASS` and exit `0`. Fork pull requests need a rule
of their own: a generated GitHub workflow carries a job-level fork guard, so a
fork PR skips the job, and a skipped job reads as a pass to branch protection;
the manual recipe has no guard and fails instead, because a fork gets no secrets.
Pair either with a human or trusted-runner review for forks, and check an
untrusted diff locally first: [Review an untrusted PR](/docs/untrusted-pr).

Secrets stay scoped per host: GitHub and Forgejo put the model key in the agent
step's `env:` and clear `GH_TOKEN`/`GITHUB_TOKEN` there, so it reaches only that
step; the GitLab job exposes the key across the job environment and its agent step
unsets the GitLab and GitHub host tokens in a subshell. `verdict` makes no model
call and never proxies the key.

## Refusals you can hit

- Exit `3` with [`missing-findings`](/docs/troubleshooting#missing-findings): findings were never recorded — check `fetch`, the agent review, and `post` all ran, then re-run.
- Exit `1` on the head dimension (`no completed post record for HEAD`): re-fetch, re-review, `post`, then re-check.

Machine readers parse the same verdict from `--json` (`data.passed` plus `data.dimensions[]`); the envelope is pinned in [JSON envelope and exit codes](/docs/json-envelope).
